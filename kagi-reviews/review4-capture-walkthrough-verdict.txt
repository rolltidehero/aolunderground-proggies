FINAL VERDICT -- CONFIRMED FINDINGS
F1 -- CRITICAL -- Control type filter mismatch blocks entire walkthrough
The .frm parser stores control types as fully qualified names such as "VB.Label" but the clickable label filter checks against bare names such as "Label". The comparison never matches. Phase 1 discovers zero clickable labels. Phase 2 receives no popup labels. The menu walkthrough is silently skipped in its entirety. This is the single largest defect in the file. Consensus: unanimous agree from all three models.
F2 -- HIGH -- QMP handshake protocol violation and unsafe command transport
The QMP connection sends "qmp_capabilities" immediately without first reading the server greeting, violating the QEMU Machine Protocol specification. The command transport method performs a single blind recv(4096) per command with no JSON parsing, no message boundary detection, no response correlation, and no handling of asynchronous events. Works by accident on local sockets with small payloads but breaks unpredictably under load or when events are interleaved. Consensus: unanimous agree, with GPT noting overlap with F4 at the pattern level.
F3 -- HIGH -- QGA guest-sync token not validated
The guest-sync command is issued with a token derived from time.time() but the response is accepted without checking that it contains the matching token. The QEMU Guest Agent protocol requires the client to discard all responses until the matching sync response arrives. Stale data from a prior session or client can be silently accepted as the sync confirmation. Consensus: unanimous agree, with Gemini citing the QGA specification directly.
F4 -- HIGH -- QGA receive assumes one recv equals one complete JSON message
The QGA transport calls sock.recv(65536) and treats the result as a single complete JSON object. TCP and Unix domain sockets provide byte streams, not message boundaries. Partial reads and multi-message reads are both possible. There is no buffering loop, no newline-delimited parsing, and no incomplete-read handling. This compounds with F3 to allow silent parsing of wrong messages. Consensus: unanimous agree.
F5 -- HIGH -- Silent success reporting from all guest command execution
The _gui_launch helper returns a success status unconditionally without checking the process return code, stdout, or stderr. The c2gui "shell" wrapper always returns returncode 0 regardless of what happened on the guest. Every downstream caller trusts these return values and proceeds as if the operation succeeded. Failures propagate silently through the entire automation chain. Consensus: unanimous agree.
F6 -- HIGH -- type_secret.py invoked on guest but not guaranteed to exist
The code invokes "C:\work\type_secret.py" via c2gui but this module contains no deployment function, no file-write step, and no existence check that would ensure the script is present on the guest before execution. Combined with F5, the secret workflow fails silently and then records a false "unlocked" entry in the manifest. Wording narrowed per GPT feedback to scope the claim to this module rather than the entire project. Consensus: unanimous agree.
F7 -- HIGH -- Submenu handler uses parent action variable instead of child action
Inside the has_kids branch, the code correctly looks up the child action with "actions.get(sub.name, '')" but then uses the variable "act", which holds the parent item's action, for the move_child_form conditional and for the manifest entry type. Submenus are labeled with the wrong action type and move_child_form may be called or skipped incorrectly. Consensus: unanimous agree.
F8 -- HIGH -- Nested control coordinates are form-relative instead of container-relative and containers are lost
The .frm parser uses a single "current" dictionary with no hierarchy tracking. When a nested Begin block is encountered (for example, a VB.Label inside a VB.PictureBox), the PictureBox record is overwritten and never saved. The label's Left and Top values are relative to its container but are added directly to the form's screen position, producing incorrect screen coordinates. Additionally, per GPT's observation, the container records themselves are actively dropped from the parsed output, meaning any control type that serves as a container is lost entirely. Consensus: unanimous agree, with GPT noting the finding may understate the damage.
F9 -- HIGH -- Guest helper scripts use bare "python" instead of PYTHON_GUEST path
The code defines PYTHON_GUEST as the full path to the guest Python interpreter but all c2gui "shell" calls for enum_windows.py, dismiss_msgbox.py, move_child.py, close_form.py, and type_secret.py use bare "python" instead. On a fresh Windows guest, "python" is typically not on PATH. Combined with F5, every one of these failures is completely silent. Consensus: unanimous agree.
F10 -- HIGH -- get_window_rects reads stale windows.json when enum script fails
The window enumeration script writes to a fixed path "C:\work\windows.json". If the script fails for any reason (wrong python path per F9, crash, permission error), the file from a previous run remains. There is no pre-deletion of the old file, no timestamp or run token, and the c2gui return code is always 0 per F5. Stale window positions are returned as current. Consensus: unanimous agree.
F11 -- HIGH -- Output manifest references files that are never created
Three sub-issues. (a) The save_crop call for the label "menu" never matches any frame because frames are labeled "menu_{name}", so screen_menu.png is never generated. (b) Secret frames are labeled "secret_{caption}" but the save loop only processes labels starting with "form_" or "dialog_", so screen_secret_*.png files referenced in the manifest are never written. (c) The elif branch for "submenu_" labels is nested inside "if imgs:" as an elif, making it unreachable when imgs is non-empty, which is the only case when the relevant data exists. Consensus: unanimous agree.
F12 -- HIGH -- screenshot_only mode does not poll for window appearance
The screenshot_only function calls _launch_proggie then performs a single get_window_rects call with no retry loop and no delay. Unlike run_walkthrough, which polls up to 100 times, this function gives the program no time to create its window. On any non-trivial VB6 program, the window will not exist yet, the function logs a message, kills the process, and returns None. The mode fails in the common case though not in every possible environment. Wording softened per GPT feedback. Consensus: unanimous agree, with GPT noting the certainty was slightly overstated.
F13 -- HIGH -- open_popup_for returns stale Phase 1 popup coordinates
The function clicks the label to open a popup but returns the popup rectangle recorded during Phase 1 without re-detecting the current popup position. If the popup appears at a different location due to refocusing, screen edge adjustment, DPI changes, or multi-monitor geometry, all subsequent hover and click calculations for menu items use wrong coordinates. Consensus: unanimous agree, with GPT suggesting lower severity for deterministic UIs. Rejected because VB6 popup placement is OS-controlled and not guaranteed stable across invocations.
F14 -- HIGH -- Phase 1 form cleanup via Escape key is unreliable for VB6 forms
When a label click opens a VB6 form during Phase 1, cleanup consists solely of sending QMP.key("escape"). Many VB6 forms do not implement a Cancel button or KeyPreview with an Escape handler, so the form remains open. Lingering forms accumulate across iterations and can obscure UI elements, interfere with popup positioning, and corrupt subsequent window detection. The severity depends on the target application population but affects a significant fraction of real VB6 programs. Wording adjusted per GPT feedback to acknowledge environment dependency. Consensus: unanimous agree.
F15 -- MEDIUM -- No check for absolute pointing device in VM configuration
The code assumes QEMU has an absolute pointing device (usb-tablet or virtio-tablet) configured. There is no capability query or fail-fast check. If the VM lacks such a device, all mouse operations silently produce no effect. Rated MEDIUM because the assumption is reasonable for the stated use case but the absence of validation creates a hard-to-diagnose failure mode. Consensus: unanimous agree on finding and severity.
F16 -- MEDIUM -- _free_process provides no meaningful delay
The _free_process function calls time.sleep(0) in a loop 100 times. In CPython, time.sleep(0) yields the GIL but does not produce any real delay. The entire loop completes in under one millisecond. Every call site that uses _free_process as a delay between poll attempts (approximately 15 locations) is effectively polling with no backoff, wasting host CPU and racing against guest operations that need actual time. Consensus: unanimous agree.
F17 -- MEDIUM -- No socket timeouts on QMP and QGA receive calls
New finding raised by Gemini. The QMP and QGA socket connections have no receive timeout configured. If the QEMU monitor or guest agent becomes unresponsive, the host script blocks indefinitely on recv() with no timeout, no cancellation, and no watchdog. In a production or batch automation context, this can cause the entire pipeline to hang forever. This compounds with F2 and F4 because the already-fragile receive logic has no escape hatch for the worst case. Consensus: raised by Gemini, not contradicted by the other two models.
